# فاز ۵ — اعتبار داخلی، معرفی مشتری، اعلان، گزارش و کنترل نقش‌ها

**وضعیت: کدنویسی ثبت‌شده در Draft PR؛ اجرای واقعی و دیباگ عمداً به مرحله نهایی موکول شده است.**
هیچ ارسال همگانی واقعی، پرداخت، برداشت، Migration یا تست شبکه در این فاز انجام نشده است.

## دفترکل اعتبار داخلی فروشگاه

- اعتبار Merchant Store Credit به **ریال صحیح** و به‌تفکیک هویت `(platform, platform_user_id)` نگهداری می‌شود.
- این اعتبار **مانده کیف پول خودِ کاربر در بله نیست**؛ API بله امکان خواندن موجودی شخصی او را برای ربات اثبات نکرده است.
- از کیف پول رمزارزی Legacy تلگرام کاملاً جداست. انتقال خودکار بین کیف پول‌ها ممنوع است.
- `ShopWalletAccount` مانده، و `ShopWalletEntry` تاریخچه تغییرناپذیر با `operation_key` یکتا را نگهداری می‌کنند.
- کاهش اعتبار زیر صفر و افزایش بیش از سقف مجاز ممنوع است. هر تغییر تحت قفل رکورد حساب و یک تراکنش انجام می‌شود.
- مشتری در هر دو ربات می‌تواند با `/wallet` یا «💳 اعتبار من» موجودی و تاریخچه کوتاه خود را ببیند.
- پرداخت سفارش با اعتبار داخلی فقط وقتی مانده برای **تمام مبلغ سفارش** کافی باشد و سفارش `approved_unpaid` باشد انجام می‌شود. قبل از کسر اعتبار، تأیید دوم مشتری ضروری است.
- کسر اعتبار، تخصیص موجودی تمام اقلام، مصرف یک‌باره Coupon، ثبت PaymentAttempt و تأیید سفارش، اتمیک هستند. در کمبود موجودی یا تخفیف، پولی کسر نمی‌شود.
- بازپرداخت اعتبار داخلی فقط از فرم مالی تأییدشده می‌آید؛ موجودی کالای احتمالاً ارسال‌شده خودکار بازنمی‌گردد.
- مدیر مالی از فرم `/admin/wallet-adjust` می‌تواند با دلیل، هویت مشخص و CSRF اصلاح ثبت کند؛ سقف پیش‌فرض **صفر** است.

## برنامه معرفی مشتری (اختیاری)

- `ShopReferralPolicy` سیاست قابل مدیریت شامل `enabled`، درصد صحیح، حداقل مبلغ و سقف پاداش است؛ پیش‌فرض **غیرفعال**.
- هر هویت پیام‌رسان کد معرفی یکتای خودش را دریافت می‌کند؛ با `/referral` نمایش داده و با `/ref CODE` توسط مشتری جدید ثبت می‌شود.
- پیش از اولین خرید موفق امکان ثبت معرف وجود دارد، نه پس از آن.
- تا زمان اتصال امن حساب‌ها، ثبت معرفی از یک پیام‌رسان به پیام‌رسان دیگر بسته است. به این ترتیب دو شناسه یکسان از دو پلتفرم یکی فرض نمی‌شوند.
- پاداش تنها پس از **اولین پرداخت موفق IRR از Provider واقعی** (`telegram_fiat` یا `bale_wallet`) و فقط یک مرتبه به اعتبار داخلی معرف اضافه می‌شود.
- خرید Stars، اعتبار داخلی، رسید ناقص، فاکتور بدون پرداخت و درخواست لغوشده هیچ پاداش ریالی نمی‌سازند.
- جبران/بازگردانی پاداش پس از Refund، سیاست ضدتقلب و Account Linking واقعی هنوز نیازمند طراحی و آزمون هستند.

## ارسال همگانی بر اساس رضایت

- `ShopIdentity.allow_announcements` برای همه کاربران جدید **False** است؛ `/subscribe` و `/unsubscribe` در هر دو پیام‌رسان تصمیم کاربر را نگه می‌دارند.
- `ShopCampaign` از SQLAdmin توسط Marketing ساخته می‌شود و تا تأیید صریح قابل ارسال نیست.
- `ShopCampaignDelivery` برای هر `(campaign, identity)` یکتا است؛ کاربران مسدود یا بدون رضایت وارد صف نمی‌شوند.
- مدیر از `/admin/campaign-review` به‌صورت دستی یک Batch حداکثر ده‌پیامی ارسال می‌کند؛ ارسال در پس‌زمینه یا Scheduler خودکار وجود ندارد.
- قبل از ارسال رضایت دوباره بررسی می‌شود؛ نتیجه ارسال موفق، `sent` و نتیجه نامشخص `unknown` است.
- هیچ پیام دارای وضعیت `sending` یا `unknown` به صورت خودکار تکرار نمی‌شود؛ این موارد نیازمند بررسی انسانی هستند.
- پیام‌ها از Bot API همان پلتفرم ارسال می‌شوند؛ Bot Tokenها در دیتابیس Campaign ذخیره نمی‌شوند.

## گزارش‌های RTL و کنترل دسترسی

- `/admin/shop-analytics`: آمار کاربران/سفارش/رسیدهای واقعی، تفکیک Telegram/Bale و بازه ۷/۳۰/۹۰ روز یا کل دوره.
- `XTR`، ریال دریافتی Provider و اعتبار داخلی مصرف‌شده از هم **جدا** گزارش می‌شوند. اعداد Legacy قبلی هنوز ادغام نشده‌اند.
- موجودی اعتبارات و پاداش‌های معرفی و وضعیت ارسال‌ها به‌عنوان مقادیر دوره‌کامل نمایش داده می‌شوند؛ «درآمد خالص» ساختگی گزارش نمی‌شود.
- حساب ثابت `admin` و Password مشترک حذف شده‌اند؛ حساب مستقل `ShopStaff` دارای Role، Hash رمز Argon2، وضعیت فعال و نسخه نشست است.
- Roleها: `superadmin`، `sales`، `content`، `finance`، `marketing`، `viewer`. هر درخواست SQLAdmin از دیتابیس اعتبار نشست را دوباره بررسی می‌کند.
- ModelViewها با دسترسی دسته‌ایِ deny-by-default حفاظت شده‌اند. صفحات اختصاصی Finance/Marketing/Sales/Content نیز Guard داخلی و CSRF دارند.
- ساخت حساب مدیر، تغییر رمز، تغییر نقش و ابطال حساب فعلاً فقط از CLI امن سرور انجام می‌شود و برای هر حساب رمز پنهان‌شده دریافت می‌شود.
- **پیش از اجرای Production:** سشن‌های قدیمی نامعتبرند و بعد از Migration باید حداقل یک Superadmin ساخته شود. هیچ رمز پیش‌فرضی وجود ندارد.

```env
TELEGRAM_STARS_CHECKOUT_ENABLED=false

```

پس از Migration روی دیتابیس آزمایشی و فقط در مرحله اجرای نهایی:

```bash
python -m scripts.manage_shop_staff add shopowner --role superadmin
python -m scripts.manage_shop_staff add marketing1 --role marketing
python -m scripts.manage_shop_staff reset-password shopowner
python -m scripts.manage_shop_staff disable marketing1
```

برای تنظیم سقف اصلاح دستی باید مدیر اصلی مقدار مثبت و محدود تعریف کند؛ با صفر عملیات مالی از UI انجام نمی‌شود.

## محدودیت‌ها و پذیرش باز

۱. تست کامل `pytest`، Migrationهای D001 و D002، و اجرای هم‌زمان تراکنش روی PostgreSQL هنوز انجام نشده است.
۲. بررسی واقعی امنیت نشست، Auth/CSRF SQLAdmin، نقش‌ها، خطر CSRF Login و مرورگر RTL باقی است.
۳. اتصال حساب‌های متعلق به یک انسان در Telegram و Bale نیازمند یک فرآیند اثبات مالکیت جداگانه است.
۴. Reward پس از Refund به‌صورت خودکار clawback نمی‌شود؛ برای فروشگاه واقعی باید سیاست ضدتقلب تعیین شود.
۵. عملیات `sending` / `unknown` کمپین باید در ابزار Reconciliation بررسی شود؛ تکرار خودکار ممنوع است.
۶. برای ده‌ها هزار کاربر، ارسال با Rate Limit/Scheduler پایدار و Delivery Receipt دقیق در مرحله مقیاس‌پذیری لازم خواهد بود.
۷. بخش Legacy فروش و کیف پول رمزارزی تلگرام هنوز حذف نشده است و در گزارش‌های جدید بدون Migration حساب نمی‌شود.
۸. Multi-bot قدیمی Telegram و مدیریت Auto-Refund بله هنوز پذیرش parity ندارند.
۹. هیچ تغییری نباید قبل از اجرای واقعی و گذراندن Test → Debug → Retest به master Merge شود.

**همه داده‌های محصول، رسانه، کمپین، پاداش، نقش و سیاست‌ها در دیتابیس هستند؛ فقط شکل ثابت منوی کاربری در کد نگه داشته می‌شود.**
