# اهداف و معیارهای پذیرش ربات فروش تلگرام و بله

> این سند مرجع نیازمندی‌های Fork است. قابلیت‌های ذکرشده لزوماً در کد فعلی پیاده‌سازی نشده‌اند؛ وضعیت هر فاز در ROADMAP ثبت می‌شود.

## مأموریت

راه‌اندازی فروشگاه و کاتالوگ محصول با **یک هسته داده و یک داشبورد مدیریتی مشترک** و دو کانال کاربری **Telegram** و **Bale**؛ بدون نیاز به طراحی داشبورد از صفر، بدون Odoo و با حداقل هزینه میزبانی.

## اصل غیرقابل مذاکره: محتوای کاملاً داینامیک

- هیچ نام، تعداد، دسته‌بندی، معرفی، توضیح، تصویر، ویدیو، فایل، رضایت مشتری، متن تجاری، قیمت، موجودی، ترتیب نمایش یا لینک پشتیبانی در سورس به‌عنوان محتوای ثابت فروشگاه تعریف نشود.
- مدیر از داشبورد بتواند محتوا را ایجاد، ویرایش، منتشر/مخفی، مرتب و حذف منطقی کند؛ بدون تغییر کد و بدون راه‌اندازی مجدد Bot Worker.
- **منوی اصلی و مسیرهای ناوبری ثابت و ساده** هستند؛ هندلرهای آن‌ها در کد باقی می‌مانند و عنوان فارسی دکمه‌ها از فایل‌های ترجمه خوانده می‌شود. **فهرست محصولات، دسته‌بندی‌ها، تعداد آیتم‌ها و محتوای هر محصول** باید کاملاً از دیتابیس تولید شوند؛ ساخت Menu Builder خارج از محدوده پروژه است.
- فایل‌های رسانه‌ای باید دارای فایل اصلی در Storage مستقل از پیام‌رسان باشند. `file_id` باید برای هر Platform، Bot و Asset جداگانه Cache شود؛ `file_id` تلگرام قابل استفاده در بله نیست.
- محتوای منتشرنشده نباید برای کاربران قابل نمایش باشد. تغییر یا حذف دسته‌بندی نباید تاریخچه خرید را تخریب کند.
- داده اولیه فقط برای تست و Fixture مجاز است؛ داده‌های مثال نباید خودکار در فروشگاه Production درج شوند.

## محدوده مدیریتی

1. مدیریت محصولات: نام، خلاصه، توضیح، SKU، دسته‌بندی، قیمت، موجودی، فعال/غیرفعال، ترتیب نمایش و وضعیت انتشار.
2. رسانه محصول: چند فایل مستقل با نوع عکس، ویدیو، صوت، سند و Caption و ترتیب انتشار.
3. رضایت‌ها: متن/رسانه، انتساب به محصول، وضعیت تأیید و ترتیب نمایش؛ بدون جعل رضایت مشتری.
4. منوی کاربری ساده و ثابت: محصولات، سفارش‌های من، پشتیبانی و بازگشت. متن‌های UI فارسی در Translation، ولی دکمه‌های محصول/دسته‌بندی از داده‌های واقعی تولید شوند؛ مدیر نیازی به Menu Builder ندارد.
5. سفارش‌ها: تاریخچه، وضعیت، آیتم‌ها، اطلاعات خریدار، پرداخت، حمل‌ونقل و رویدادهای قابل ممیزی.
6. داشبورد: فارسی راست‌به‌چپ، طراحی واکنش‌گرا، جستجو/فیلتر، سطوح دسترسی و ثبت فعالیت مدیریتی.
7. تنظیمات کانال: اتصال/قطع اتصال هر ربات، وضعیت سلامت و تنظیمات پیام‌رسان بدون افشای Token.
8. تحلیل: مشاهده فروش و بازدیدهای منتسب به هر پلتفرم بدون دوباره‌شماری مشتریان.

## معماری هدف

- Backend: Python 3.12، FastAPI، SQLAlchemy async، PostgreSQL و Alembic.
- Admin: SQLAdmin با قالب راست‌به‌چپ فارسی؛ مهاجرت Framework مدیریتی فقط پس از بررسی فنی.
- Core Services: `Catalog`، `Media`، `Testimonials`، `Orders`، `Payments`. ناوبری ثابت با Handlerهای اختصاصی و ترجمه فارسی انجام می‌شود.
- Channels: `TelegramAdapter` و `BaleAdapter` باید **موازی و هم‌سطح** توسعه و تست شوند؛ Core نباید از `aiogram.types` یا `telegram_id` برای مدل هویت مشتری استفاده کند.
- Identity: `(platform, platform_user_id)` برای هر هویت پیام‌رسان، با اتصال اختیاری حساب‌های یک مشتری.
- Storage: فایل اصلی روی دیسک پایدار یا Object Storage؛ شناسه پیام‌رسان صرفاً Cache ارسال باشد.
- Security: RBAC، محدودسازی آپلود، کنترل نوع و اندازه فایل، محافظت از Webhook، عدم ثبت Token در لاگ، CSRF برای فرم‌های مدیریتی، Backup و Audit Log.
- Performance: یک VPS در فاز شروع، سرویس‌های حداقلی، محدودیت نرخ درخواست، و افزودن Worker/Queue تنها با ضرورت عملی.

## پذیرش عملکردی

- مدیر بتواند هر تعداد محصول را با تعداد متغیر رسانه و رضایت از داشبورد ایجاد کند.
- تغییر عنوان، توضیحات، فایل، قیمت و ترتیب **محصولات و رضایت‌ها** هنگام بازکردن دوباره کاتالوگ تلگرام و بله قابل مشاهده باشد؛ **بدون Deploy**. تغییر ساختار دکمه‌های اصلی مستلزم تغییر کد است و جزو نیازهای مدیر محتوا نیست.
- داشبورد مدیریتی فارسی و RTL باشد؛ متن‌های فارسی ربات خوانا باشند و شناسه‌ها، اعداد، کد محصول و لینک‌ها جهت صحیح داشته باشند.
- یک Product و رسانه‌های آن در هر دو کانال محتوای یکسان داشته باشد؛ فایل Cache هر کانال مستقل باشد.
- سفارش برای دو خرید هم‌زمان از موجودی بیش از حد تخصیص ندهد؛ مبلغ با Decimal محاسبه و وضعیت پرداخت Idempotent ثبت شود.
- مدیر به داده/عملیات خارج از Role خود دسترسی نداشته باشد؛ تمامی عملیات حساس در Audit ثبت شوند.
- مسیرهای Migration روی دیتابیس موجود اجرا شوند و تاریخچه خرید بدون تغییر نگه داشته شود.
- Unit، Integration و تست واقعی Telegram/Bale برای هر Release ثبت شوند؛ هیچ قابلیت بدون تست «تکمیل‌شده» اعلام نشود.

## قرارداد محصول

- نوع محصول فیزیکی، دیجیتال یا هر دو قابل پشتیبانی باشد؛ شیوه پرداخت مطابق سیاست پلتفرم و نوع کالا انتخاب شود.
- پرداخت رمزارزی، کیف پول و Referral موجود در upstream فعلاً **اختیاری و خارج از MVP** هستند، نه بخشی از تجربه اجباری کاربر.
- مشخصات فروشنده، محصول و رسانه باید واقعی و قابل ویرایش باشند. هیچ ادعای پزشکی، امتیاز یا رضایت ساختگی تولید نشود.
- قابلیت سفارش‌گیری ابتدا فقط با روش سفارش مورد تأیید کسب‌وکار فعال شود؛ فعال‌سازی درگاه پرداخت نیازمند تست Gateway و Webhook است.

## محدودیت‌های شناخته‌شده upstream

- منوی اصلی از `run.py` و `KeyboardButton` ساخته می‌شود. این رویکرد برای MVP **حفظ** می‌شود؛ تنها ترجمه فارسی متن‌های UI و نمایش داینامیک داده‌های محصولات لازم است.
- `Item` فعلی تقریباً معادل واحد موجودی است و موجودیت مستقل Product/Asset ندارد.
- رسانه‌ها به دسته/زیردسته/دکمه وصل‌اند؛ Library چندرسانه‌ای محصول وجود ندارد.
- `Review` متصل به `BuyItem` است و برای رضایت‌های قابل انتشار مستقل مناسب نیست.
- SQLAdmin 0.22.0 ترجمه فارسی آماده ندارد؛ باید در Fork محلی‌سازی شود.
- شناسه کاربر و بسیاری از سرویس‌ها Telegram-specific هستند و اتصال بله صرفاً تغییر Base URL نیست.
