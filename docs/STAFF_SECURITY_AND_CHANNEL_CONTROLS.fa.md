# امنیت کارکنان و کنترل‌های فروشگاه دوپیام‌رسانه

> وضعیت: پیاده‌سازی سورس روی شاخهٔ آزمایشی، **تست Docker/PostgreSQL/مرورگر واقعی هنوز انجام نشده**. PR را Draft نگه دارید.

## دامنهٔ تغییر

- نقش‌های `superadmin` و `finance` باید در اولین ورود MFA/TOTP فعال کنند. تا تکمیل ثبت MFA، تنها مسیرهای لازم برای مشاهدهٔ حساب، تنظیم TOTP و خروج فعال هستند.
- ایجاد کارکنان با رمز تعیین‌شده توسط مدیر حذف شده است. مدیر لینک دعوت یک‌بارمصرف (۴۸ ساعت) می‌سازد، می‌تواند دعوت را لغو کند و شخص دعوت‌شده خودش رمز را تنظیم می‌کند.
- Reset رمز توسط مدیر فقط با لینک یک‌بارمصرف ۳۰دقیقه‌ای است. Redeem تمام نشست‌های قبلی را بی‌اعتبار می‌کند و لینک قابل استفادهٔ مجدد نیست. لینک‌ها در DB فقط به شکل SHA-256 ذخیره می‌شوند.
- سیاست رمز (حداقل ۱۲ تا ۶۴ نویسه و چهار قاعدهٔ اختیاری) از پنل تنظیم می‌شود. روی **رمزهای جدید** اعمال می‌شود، بدون اینکه هش قبلی کاربران را بازنویسی کند.
- Audit مدیران با فیلتر عامل، نوع رویداد، بازهٔ زمانی و صفحه‌بندی. رمزها، توکن‌های دعوت، QR/TOTP و محتوای درخواست در Audit ذخیره نمی‌شوند.
- هدر پنل دکمهٔ «حساب من» دارد و گزینهٔ timezone از فهرست استاندارد IANA انتخاب می‌شود.
- محصول و رسانه همان فرم اصلی جدید Codespaces را دارند: SKU و توضیحات اختیاری؛ Many2one دسته‌بندی با جست‌وجو، ساخت و ویرایش؛ ارسال چند رسانه با Drag & Drop و حفظ وضعیت خصوصی تا انتشار.
- «سبد خرید» و «اعتبار داخلی فروشگاه» به تفکیک `telegram` / `bale` قابل فعال/غیرفعال‌سازی‌اند. نام نمایشی اعتبار داخلی نیز مستقل است. تمام سوابق `shop_carts`، `shop_wallet_entries`، سفارش‌های قبلی و دارایی مشتری حفظ می‌شوند.

## مرز مهم

اعتبار داخلی فروشگاه با **Bale Wallet خارجی** و **Telegram Stars** یکی نیست. تنظیمات کنونی فقط اعتبار داخلی را کنترل می‌کنند؛ اضافه/حذف کردن Credentialها و درگاه‌های خارجی جزو این PR نیست. قابلیت‌های ربات بله و تلگرام به یکدیگر وصل نشده‌اند، مگر آنکه مالکیت دو حساب در جریان مستقلی ثابت شود. شناسهٔ عددی یکسان در دو Provider به معنی شخص یکسان نیست.

## مدل‌ها و Migration

| مدل | هدف |
| --- | --- |
| `shop_password_policy` | سیاست رمز مشترک |
| `shop_staff_invitations` | دعوت یک‌بارمصرف با تاریخ انقضا و قابلیت لغو |
| `shop_staff_password_resets` | بازیابی یک‌بارمصرف و ابطال نشست‌ها |
| `shop_channel_features` | گزینه‌های سبد خرید و اعتبار داخلی برای هر Provider |

برای پایگاه Production فقط Alembic `20261103g001` سپس `20261103h001` روی نسخهٔ سازگار و پس از پشتیبان‌گیری به‌کار می‌رود. در Codespaces از `scripts.security_bootstrap` و allowlist جدول‌های افزایشی استفاده می‌شود. هیچ بازنشانی یا تغییر مخفیانهٔ داده‌ها مجاز نیست.

## پذیرش فنی؛ همه باید PASS شوند

1. با مشخصات دسترسی آزمایشی و بدون Token ربات، دستورهای پایتون `pytest -q tests/test_admin_control_plane.py tests/test_staff_security_lifecycle.py tests/test_next_admin_operations_offline.py` و مجموعهٔ کامل `pytest -q` اجرا شوند.
2. `cd dashboard-next && npm run typecheck && npm run lint && npm run build` در محیط دارای Node و dependencyهای نصب‌شده اجرا شود.
3. PostgreSQL واقعی: ساخت و لغو دعوت، expire واقعی با ساعت کنترل‌شده، Redeem موفق یک‌بار، Redeem مجدد 410، Reset پسورد و ابطال نشست قدیمی در مرورگر دوم.
4. MFA: حساب بدون TOTP با نقش حساس، تنها حق setup/confirm داشته باشد؛ پس از فعال‌سازی با TOTP صحیح اجازهٔ کار بگیرد؛ غیرفعال‌کردن MFA برای همان نقش رد شود؛ session revocation همچنان معتبر باشد.
5. RBAC: نقش viewer/sales نتواند سیاست رمز، Audit، ایجاد دعوت و تغییر تنظیمات Providerها را بخواند یا تغییر دهد.
6. در مرورگر، RTL در ۳۲۰، ۷۶۸، ۱۴۴۰ پیکسل؛ پروفایل، Select timezone، جدول کارکنان، جست‌وجو، Modal و Breadcrumb دسته‌بندی، فرم محصول و Drag & Drop فایل‌ها بررسی شوند.
7. روی هر پیام‌رسان جداگانه: خاموش کردن سبد باید درخواست تازه و callback قدیمی را رد کند، بدون حذف سبد قبلی؛ خاموش کردن اعتبار باید استفادهٔ تازه را رد کند و پرداختِ قبلاً قطعی و تراکنش‌های مرجوعی را دست‌کاری نکند.
8. آپلود ۱۱ فایل، فایل بیش‌ازحد، نوع ناشناخته، و یک فایل معتبر در Codespace آزمایش شوند؛ تأیید انتشار فقط فایل همان محصول را تغییر دهد.
9. خطای ثبت محصول در مسیر `/api/admin/products` به پاسخ امن با `requestId` تبدیل شود. پیکربندی بیرونی (Webhook، Polling) و پرداخت حقیقی بدون تأیید مستقل لمس نشوند.
10. تست UI با Playwright و `next-dev-loop` روی Codespace فعال اجرا شود و نتیجهٔ واقعی در PR مستند گردد.

**توجه امنیتی:** اگر کلید TOTP در اسکرین‌شات‌های ارسالی، کلید فعال یک حساب واقعی است، آن را افشاشده تلقی کرده و قبل از استفادهٔ عملیاتی TOTP را از نو ثبت کنید.
